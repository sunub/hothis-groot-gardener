# 재배 시간축과 사건 계획

Space Garden Simulator · 2026-11-15 · 초안

'80억 분의 1'(https://1in8b.life/ko/)의 방식을 참고해, 이 게임에 두 가지를 더하려고 합니다. 하나는 재배일이 흐르는 시간축이고, 다른 하나는 그 흐름 속에서 조건이 맞을 때 나는 사건입니다. 이 문서는 지금 기획을 무너뜨리지 않고 넓히는 방향만 다룹니다. 다음 순서로 정리했습니다. 무엇을 그대로 두고 무엇을 더하는지, `data/vector_db`의 자료로 어떤 사건을 만들 수 있는지, 그리고 세 역할(시뮬레이션 둘, 화면 하나)이 어떻게 나눠 동시에 진행할지입니다.

## 1. 기본 원칙

1. **판정과 수치는 지금처럼 근거 목록이 정합니다.** 조치의 판정, 수치 변화, 사건이 날 확률은 `data/content/evidence.json`과 `data/content/events.json`에 고정합니다. 화면에는 "게임 값"으로 표시합니다.
2. **DB(RAG)는 사건을 고르고 글을 쓰는 데에만 씁니다.** 장면 설명, 단서, 식물의 말, 판정 뒤 해설이 여기에 해당합니다. DB 자료로 판정을 내리지 않습니다.
3. **지금의 수치 균형을 유지합니다.** 밤사이 변화는 지금처럼 게임 날마다 한 번 적용합니다. 게임 날 사이의 재배일에는 사건 판정만 합니다. 그래서 결정 목록 13번과 14번의 수치, 엔진 테스트의 기대값이 그대로 유지됩니다.
4. **원문에 없는 일은 지어내지 않습니다.** 원문이 수치나 기준을 주지 않는 곳은 팀이 정한 게임 값으로 두고, 그렇다고 화면에 밝힙니다.

## 2. 참고한 게임: '80억 분의 1' (직접 플레이해 수집)

2026-11-15에 Chrome에서 v0.10.19 베타를 직접 플레이했습니다. 이미 진행 중이던 삶(인도, 여성)을 10세부터 22세까지 이어서 살았고, 그동안 결정 카드 12장, 멈춤 카드 1장, 자동 기록 30여 줄을 기록했습니다. 아래 내용은 화면에서 직접 확인한 것입니다. 확률 공식 같은 내부 계산은 화면에 나오지 않아 확인하지 못했습니다.

### 2.1 시간 흐름

- 화면 위에 나이와 연도, "1년 ≈ 3초"가 표시됩니다. 조작 단추는 `계속/멈춤`, `1×~16×`, `다음 결정까지 »`, `자동 결정`입니다.
- `다음 결정까지 »`를 누르면 다음 결정 카드가 나올 때까지 빠르게 흐릅니다. 10세에서 14세까지 약 5초가 걸렸습니다.
- **결정을 미루면 시간이 멈춥니다.** `잠깐 내려 두기`를 누르면 카드가 접히고 아래에 "결정을 기다리고 있어요 · 다시 펼치기" 띠가 남습니다. 16배속이어도 나이가 오르지 않았습니다.
- **정해진 나이에 멈춤 카드가 뜹니다.** 15세에 "잠시 멈춤" 카드가 떴습니다. 카드에는 다음이 들어 있었습니다.
  - 나라 통계 (기대 교육연수, 18세 전 결혼 비율)
  - "같은 1초에 태어난 사람들"의 현재 상태
  - 돌아보는 질문 ("열다섯 살의 당신에게 학교는 어떤 곳이었나요?")과 글 입력 칸
  - 선택지: `적어 두고 계속 살기`, `마음속에 담고 계속 살기`, `다음부터 이 창 띄우지 않기`

### 2.2 사건의 세 종류

| 종류 | 관찰한 예 | 형식 |
|---|---|---|
| **결정 카드** ("중대 결정") | 고등학교 진학, 새 취미, 졸업 뒤 진로, 재수, 전공, 중매, 출산, 졸업 후, 첫 직장 | 아래 2.3 참고 |
| **자동 기록** (선택 없음) | 축제(+), 친구(+), 휴대폰 도난(−), 열대야(−), 부모님의 이혼, 오빠의 결혼, 세계 경기 침체, 재수 시작(±) | 나이, 한 줄 글, 끝에 `+`/`−`/`±` 표시. 일부는 아래에 **자료** 줄이 붙음 |
| **비교 기록** | "15세. 같은 해 인도에서 태어난 여자아이 중 약 97%가 지금도 살아 있습니다." / "같은 1초에 태어난 나이지리아의 Inna가 17세에 세상을 떠났습니다. (패혈증)" | 통계나 같은 날 태어난 다른 삶과 비교 |

- **자료 줄은 출처를 밝힌 통계입니다.** 예를 들어 부모님의 이혼 아래에는 "OECD 나라 평균 12~17세 아이의 약 23%가 한 부모와 삽니다 (OECD Family Database)"가, 경기 침체 아래에는 "금융 위기는 나라마다 한 해 약 2% 꼴 (IMF; Laeven·Valencia 2018)"이 붙었습니다.

### 2.3 결정 카드의 구조

```
중대 결정                         19세 · 2045년   [잠깐 내려 두기 ▾]
다시 보는 입시                                          ← 제목(질문)
한 해 더 준비했습니다. 이번에는 어떻게 할까요?            ← 상황 한 줄
┃ 이 나라 같은 세대 중 대학을 마치는 비율은 약 25% …      ← 통계 상자(출처), 고르기 전에 보임
1 대학 입시에 도전한다   붙을 가능성 반반쯤 · 지식 48 · 형편과 정원에 따라
2 바로 취업한다         일찍 돈을 번다
3 해외 유학을 떠난다     비용이 크지만 기회도 크다
                [이제부터 결정을 자동으로 맡기기]
```

- 선택지는 2~5개입니다.
- 선택지마다 **힌트 줄**이 있습니다. 힌트에는 세 가지 형태가 있었습니다.
  - 지금 능력치에 따른 가능성 (예: "가능성 반반쯤 · 지식 46")
  - 효과의 방향 (예: "행복+ 건강+ 돈이 듦", "행복↑ 양육비↑")
  - 비용 (예: "약 1.0억 원", "연 $10,470 PPP · 한국 체감 월 74만 원")
- 다시 나오지 않게 하는 선택지가 있습니다 ("아이 없이 살기로 한다 · 다시 묻지 않아요").
- **결과는 고른 즉시 기록에 남습니다.** "결정: 대학 입시에 도전한다" 줄 바로 다음에 결과 줄 "대학 입시에서 떨어졌습니다.−"가 붙고, 능력치가 바로 바뀝니다 (행복 68 → 60).

### 2.4 사건이 이어지는 방식

실제로 이어진 순서는 다음과 같습니다.

1. 18세 진로 카드에서 입시를 골랐고, 떨어졌습니다 (확률로 정해진 결과).
2. **바로** 다음 카드 "다시 도전할까?"가 떴습니다 (재수 / 취업).
3. 재수를 고르자 자동 기록 "학원에 다니며 한 해 더 공부하기로 했습니다.±"가 남았습니다.
4. **정확히 1년 뒤** 카드 "다시 보는 입시"가 떴고, 이번에는 합격했습니다 (행복 58 → 65).
5. 이어서 "무엇을 공부할까요?" → 졸업 → "졸업 후" → "첫 직장을 고르세요"로 이어졌습니다.

정리하면 결과가 다음 사건을 부르는 방식은 두 가지입니다. 결과 직후에 바로 뜨는 **즉시 후속**과, 정해진 시간이 지난 뒤 뜨는 **예약 후속**입니다.

### 2.5 계속 유지되는 설정: "올해의 초점"

- 언제든 바꿀 수 있습니다. 선택지마다 효과 방향이 붙어 있습니다.
- **나이에 따라 선택지가 바뀝니다.**
  - 학생 때: 공부(지식↑ 행복↓), 친구·놀이(관계↑ 행복↑), 집안 돕기(가족↑ 지식 조금↓), 운동(건강↑), 취미(행복↑ 취미 실력↑)
  - 졸업 뒤: 가족·친구(관계↑ 행복↑), 건강 관리(건강↑ 돈 조금↓), 자기계발(지식↑ 행복 조금↓), 취미, 휴식(건강↑ 행복↑)
- 상황이 바뀌면 게임이 초점을 대신 바꾸고 기록에 남깁니다 ("일자리를 찾는 동안 '공부' 대신 '자기계발'에 마음을 쏟기로 했습니다.").
- **효과는 해마다 조금씩입니다.** '공부'로 1년을 보내니 지식 47 → 48, 행복 60 → 58이었습니다. 다른 사건의 효과와 섞인 값입니다.
- 도움말의 설명: "높은 수치는 가능성을 높일 뿐 결과를 정해 주지는 않아요."

### 2.6 화면 구성

- 장면 그림과 사는 곳 한 줄
- 능력치 막대 4개, 초점, 돈 쓰기
- **인생 기록**: 최근 것이 위에 오고, 줄마다 ☆ 표시를 할 수 있음
- 같은 1초에 태어난 4명의 현재 상태 (세상을 떠나면 † 표시와 원인)
- **인생 지도**: 한 칸이 1년이고 아이콘으로 표시하며, 테두리 칸은 기대수명
- **생존 곡선**: "22세까지 살아 있을 확률 96%"
- 나라 통계표와 출처 목록

### 2.7 우리 게임에 옮길 것과 옮기지 않을 것

| 관찰한 것 | Space Garden에 옮기는 방법 | 기존 기획과의 관계 |

| 결정을 미루면 시간이 멈춤 | 사건 카드가 떠 있는 동안 시간축을 멈춤. 접으면 "대응을 기다리는 중" 띠를 남김 | 더함. 지금의 `crisis` 단계와 같은 뜻 |
| 정해진 나이의 멈춤 카드와 돌아보는 질문 | 게임 날 7개를 멈춤 지점으로 삼고, 실험 기록 비교와 돌아보는 질문을 보여 줌. 답은 선택 | 더함. 판정과 무관 |

| 같은 1초에 태어난 사람들 | **같은 날 시작한 실제 실험**: VEG-01A, VEG-01B, VEG-03A, VEG-03J의 기록을 내 재배와 나란히 보여 줌 (예: "VEG-01A는 14일째 5포기 중 3포기의 생장이 멈췄습니다.") | 더함. DB의 날짜 기록을 그대로 씀 |

| 즉시 후속과 예약 후속 | 즉시 후속: 지금의 "부적절하면 다시 제시". 예약 후속: 지금의 "부분적이면 다음 날 같은 위기 확률 +30%p"를 사건으로 표현 | 기존 규칙을 사건 형식으로 옮김 |

| 결과를 확률로 정함 (입시 합격/불합격) | **옮기지 않음.** 판정은 근거 목록으로 고정. 무작위는 사건이 나는지에만 씀 | 원칙 1 유지 |
| 자동 결정 | 교육용 기본 화면에서는 뺌. 시연 모드에서만 고려 | 선택 |
| 끝없이 이어지는 사건 | 33일 안에서만 진행 | 옮기지 않음 |

`data/vector_db`에는 `plant_research` 컬렉션 하나가 있고, chunk는 81개입니다. 원본은 `data/sources/total_RAG.json`입니다.

### 먼저 해결할 문제

1. **라이선스.** 81개 가운데 56개 chunk의 `source_license`가 비어 있습니다. VEG-03J를 가장 먼저 확인해야 합니다. 결정 목록에서도 비상업 조건 자료(Schuerger)는 데이터로 쓰지 않았습니다.
2. **곰팡이 위기의 근거가 DB에 없습니다.** 지금의 과습·곰팡이 위기는 백일홍(VEG-01C) 기록에 기대는데, 그 chunk가 DB에 없습니다. 대신 팬 고장과 잎 물방울 chunk가 있어서 원인 쪽 근거는 오히려 단단해집니다.
3. **DB의 수치를 판정 기준으로 쓰면 안 됩니다.** 여러 chunk의 메모가 이를 막고 있습니다. 예를 들어 "이 표의 값에서 조절 조치를 시작할 기준을 정할 수는 없다", "회복을 보장하지 않는다"고 적혀 있습니다.
4. **물 부족 위기와 같은 사건입니다.** `veg01-stall-a/b`는 지금 물 부족 위기의 근거(Massa 2014)와 같은 VEG-01 사건입니다. 두 근거를 합칠지, 하나로 바꿀지 정해야 합니다.
5. **검색 품질.** 한국어 번역 폴더 `data/sources/json_ko`가 저장소에 없습니다. 지금은 검색 방식 가운데 단어 일치 검색(BM25)이 영어 원문만 찾으므로, 한국어 질문의 검색 품질이 떨어집니다.

## 4. 제안하는 구조

```
재배일 0 ──▶ 1 ──▶ 2 ──▶ 3 ─────────▶ 6(게임 2일째) ──▶ … ──▶ 33(수확)
             │            │       │        │
          [조건 검사]  [예정 사건] [기록]  [멈춤 카드: 실험 비교 + 돌아보는 질문]
             │       "심지 벌리기"  "VEG-03J는   [일상 돌봄 + 위기 판정 + 밤]
             │                     이날 …"
       조건 맞음 → 사건 카드(시간 멈춤) → 환경 조작으로 대응 → 근거 목록으로 판정
                         └ 접어 두면 "대응을 기다리는 중" 띠, 시간은 계속 멈춤
```

- **멈춤 지점.** 7개 게임 날(재배일 1, 6, 12, 17, 22, 28, 33)이 시간이 멈추는 지점이 됩니다. 여기서 일상 돌봄, 위기 판정, 밤사이 변화가 지금과 똑같이 일어납니다.
- **예정 사건.** 정해진 재배일에 반드시 납니다. 심지 벌리기, 솎기, 수확 절차가 여기에 속합니다. 근거가 단단해서 시연에 쓰기 좋습니다.
- **조건 사건.** 기간, 상태 조건, 확률이 모두 맞을 때 납니다.
- **사건 연결.** 조건 사건이 남긴 표시가 다음 수치를 바꾸고, 그 결과 기존 위기의 조건이 맞게 됩니다.
  - 급수 장애(`water_blocked`) → 급수해도 뿌리 수분이 늘지 않음 → 물 부족 위기
  - 팬 고장(`fan_actually_off`) → 밤사이 습도가 5 더 오름 → 과습·곰팡이 위기
- **목표 사건까지 시간 흘리기.** 엔진에 `advanceUntilEvent(state)`를 더합니다. 재배일을 하나씩 넘기며 사건 조건을 검사하고, 사건이 나거나 다음 게임 날에 닿으면 멈춥니다. 화면에는 일시정지, 배속, "다음 사건까지" 단추를 둡니다.
- **대응 방식.** 사건에는 급수와 팬 조작으로 대응하고, 새 절차 조작(심지 벌리기, 솎기, 패드 교체, 팬 작동 확인)을 더합니다. 이것은 이전 분석의 B안입니다. 판정은 조작을 조치 이름으로 바꿔 근거 목록에서 찾습니다.

플레이에서 확인한 방식(2.7절)을 더하면 다음과 같습니다.

- **사건이 떠 있는 동안 시간은 멈춥니다.** 카드를 접어 둘 수는 있지만, 대응하기 전까지 시간축은 움직이지 않습니다. 지금의 `crisis` 단계와 같은 규칙이라 엔진 규칙은 바뀌지 않습니다.
- **기록 사건 (선택 없음).** 시간이 흐르는 동안 기록에 한 줄씩 남습니다. 끝에 `+`/`−`/`±` 표시를 붙이고, 출처가 있으면 아래에 **자료** 줄로 DB chunk의 출처를 붙입니다. 사건이 없는 날도 기록이 이어져 시간이 흐르는 느낌을 줍니다.
- **같은 날 시작한 실제 실험.** '80억 분의 1'의 "같은 1초에 태어난 사람들"처럼, VEG-01A, VEG-01B, VEG-03A, VEG-03J의 기록을 내 재배와 나란히 보여 줍니다.
  - 예: 내 재배가 14일째에 닿으면 "VEG-01A: 5포기 중 3포기의 생장이 멈췄습니다"가 기록에 뜹니다.
  - 데이터는 `events.json`의 `parallel_tracks`(5절)에 있습니다. 수치는 원문 그대로이고 "실측"으로 표시합니다.
- **멈춤 카드.** 게임 날 7개에 멈춤 카드를 띄웁니다. 카드에는 지금 상태 요약, 같은 날의 실제 실험 기록, 돌아보는 질문 하나(답은 선택)를 넣습니다. 판정이나 수치와는 무관하고, "다음부터 띄우지 않기"를 둡니다.
- **조작 단추의 효과 방향.** 초점 선택지처럼 조작 단추에 효과 방향을 붙입니다 (예: 팬 강: 습도↓ 뿌리 수분↓, 급수 많이: 뿌리 수분↑↑). 숫자는 이미 있는 밤사이 예상값 화면이 보여 줍니다.
- **위기 선택지에는 힌트를 붙이지 않습니다.** '80억 분의 1'은 선택지마다 가능성과 효과를 미리 보여 주지만, 우리는 고른 뒤에 판정을 보여 주는 학습 설계를 유지합니다. 고르기 전에 보여 주는 것은 상황, 단서, 실제 실험의 기록(통계 상자 자리)까지입니다.

### DB(RAG)의 자리

| 역할 | 맡는 곳 |
|---|---|
| 사건이 나는지, 판정, 수치 변화 | `events.json`과 `evidence.json` (고정, 출처 있음) |
| 장면 설명, 단서, 식물의 말, 판정 뒤 해설 | LLM과 그 사건의 `source_chunks` |
| 자유 질문 ("지금 뭘 해야 해?") | `rag_llm.py`의 검색 전체. 나중에 더할 기능 |

사건마다 쓸 chunk를 미리 골라 파일로 내보냅니다(예: `data/content/event-chunks.json`). 그러면 Next.js 앱이 Python을 실행하지 않아도 됩니다. 앱의 위기 API는 이 파일의 chunk 본문을 LLM에 넘기기만 하면 됩니다. 모델 호출이 아직 없는 `apps/web/src/server/ai/crisis/generator.ts` 자리가 여기에 해당합니다. 출력은 지금의 검증(`apps/web/src/server/ai/crisis/validate.ts`)을 그대로 통과해야 합니다.

|---|---|---|

**팀이 정할 것**
- 각 사건 조치의 판정과 수치 변화. 원문은 절차만 적고, 건너뛰었을 때 결과는 적지 않습니다.
- 확률 15%, 20%, 25%와 팬 고장 때 습도 +5.
- "팬을 강으로"가 팬 고장 표시를 지우는지. 원문에는 이에 대한 내용이 없습니다.
- 해가 없는 사건(`mild_tip_burn`)을 넣을지. 눈에 보이는 변화가 늘 위기는 아니라는 점을 알려 주는 사건입니다.

## 7. 작업 분담 (3역할: 시뮬레이션 2 + 화면 1)

역할은 사람이나 계정이 아니라 **폴더 경계**로 나눕니다. 시뮬레이션과 데이터 쪽은 두 역할(A, B)이 나눠 맡고, 화면과 콘텐츠는 한 역할(C)이 맡습니다. 누가 어느 역할을 맡아도 되고, 작업 묶음 단위로 이어받을 수 있습니다. 세 역할이 함께 고치는 파일은 0단계에서 고정하는 계약 파일뿐입니다.

### 7.1 세 역할과 맡는 폴더

| | 역할 A: 시뮬레이션 엔진 | 역할 B: 데이터와 생성 | 역할 C: 화면과 콘텐츠 |
|---|---|---|---|
| 한 줄 요약 | 시간이 흐르고 사건이 나며 상태가 바뀌는 규칙 | 근거 데이터, RAG, 위기 API, LLM 생성 글 | 보이는 모든 것, 화면 글, 그림 |
| 맡는 폴더 | `apps/web/src/lib/game/**`, `apps/web/src/lib/events/**`(스키마, 읽기, 사건 판정), `apps/web/src/lib/evidence/select.ts`, `apps/web/src/features/mission/**`(임무 상태 저장소, 단계 이동) | `data/content/*.json`, `apps/web/src/lib/evidence/check.ts`, `apps/web/src/server/ai/crisis/**`, `apps/web/src/app/api/**`, Python RAG(`retriver.py`, `reranker.py`, `rag_llm.py`, `build_vector_db.py`, `evaluation.py`), `data/vector_db/`, `data/json/` | `apps/web/src/features/**`(`mission` 제외), `apps/web/src/components/**`, `apps/web/src/app/**`의 페이지, `public/**`, `apps/web/src/lib/i18n/**`, `docs/DEMO-SCRIPT.md` |
| 테스트 | 엔진, 사건, 저장, 시나리오 | 근거 목록 점검, 위기 파이프라인, 사건 목록 점검, RAG | 화면 테스트 |

`apps/web/src/features/mission/**`는 화면 폴더 안에 있지만 임무 상태를 저장하고 엔진을 부르는 코드라 A가 맡습니다.

### 7.2 함께 쓰는 계약 파일

| 파일 | 작성 | 검토 | 바꾸는 방법 |
|---|---|---|---|
| `apps/web/src/lib/contract/types.ts` (공용 타입) | A | B, C | A가 PR을 열고 두 역할이 승인한 뒤 병합. 예시 데이터도 같은 PR에서 고침 |
| `apps/web/src/lib/contract/schemas.ts` (API·AI 출력 검증) | B | A | 타입이 바뀌면 B가 같은 PR이나 바로 다음 PR에서 맞춤 |
| `apps/web/src/lib/contract/fixtures.ts` (예시 상태 데이터, 새 파일) | A | C | C는 이 데이터로 엔진 없이 화면을 만듦 |
| `data/content/events.json` | B (내용: 수치, `source_chunks`, 실험 기록) | A (형식이 스키마와 맞는지) | 형식은 A의 `apps/web/src/lib/events/schema.ts`가 정함. 수치는 S2 팀 결정이 있어야 바꿈 |
| `data/content/event-chunks.json` (새 파일) | B | A, C | 형식은 S1에서 정함 |

**글은 사전 파일로 옮깁니다.** 이 프로젝트는 화면 글을 모두 `apps/web/src/lib/i18n`의 사전에 둡니다. `events.json`의 `name`, `scene_hint`, `parallel_tracks[].text`는 `apps/web/src/lib/i18n/en/events.ts`(C 담당)로 옮기고, `events.json`에는 `event_id`와 출처 참조만 남깁니다.

### 7.4 작업 방식

- 기준 브랜치는 `origin/sunub`(통합 브랜치)입니다. 묶음마다 브랜치를 만들고(예: `feat/A3-advance-until-event`, `feat/B4-event-chunks`, `feat/C2-event-card`), 끝나면 통합 브랜치로 PR을 엽니다.
- PR을 병합하기 전에 `npm run check`(타입 검사, 린트, 테스트, 빌드)가 통과해야 합니다. Python 쪽은 `uv run python -m unittest test_rag_llm`입니다.
- 계약 파일이 바뀌면 7.2의 검토 역할이 승인합니다. 이미 병합된 타입을 바꿀 때는 예시 데이터를 함께 고쳐, 다른 역할의 화면이나 테스트가 깨지지 않게 합니다.
- A와 B의 경계에서 지킬 것:
  - **A는 데이터 파일을 직접 고치지 않습니다.** 형식이 바뀌면 스키마를 바꾸고 B에게 알립니다.
  - **B는 엔진 규칙을 고치지 않습니다.** 수치는 데이터 파일로만 바꿉니다.
- `events.json`의 수치는 S2 팀 결정 없이는 바꾸지 않습니다.

## 8. 순서와 동시 진행

```
0단계 (함께)  S1 계약 고정 ───────────────────────┬── S2 수치 결정
                                                  │
역할 A  A1 → A2 → A3 ─────────────→ A4 · A5 (S2 뒤)
역할 B  B1 · B2 · B3 (지금 시작) ──→ B4 → B5         B6 (S2 뒤)
역할 C  C4 · C5 (지금 시작)   C1 · C2 · C3 · C6 (S1 뒤, 예시 데이터로)
                    │                │
통합                └─ I1 (A3 + C1~C3) ── I2 (B5 + C2) ── I3 (A4·A5 + 시연)
```

- **지금 바로 시작할 수 있는 것:**
  - B1(출처 확인), B2(사건별 검색 확인), B3(DB 보강)
  - C4(효과 방향), C5(그림)
  - 계약 파일과 무관하므로 A가 S1을 준비하는 동안 B와 C가 먼저 움직일 수 있습니다.
- **S1이 끝나면:** A는 엔진을, B는 근거 묶음과 생성 글을, C는 예시 데이터로 화면을 만듭니다. 세 역할이 서로 기다리지 않습니다.
- **S2를 기다리는 것:** A4, A5, B6.
- **결정 목록의 코드 고정(11/15 18:00) 전:** 게임 동작을 바꾸지 않는 B1, B2, B3만 하는 편이 안전합니다.
